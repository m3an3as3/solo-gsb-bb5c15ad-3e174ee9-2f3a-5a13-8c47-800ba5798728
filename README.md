# 演出道具交接核验 Web 应用

用 **Node.js（Express）+ 原生 HTML/CSS/JavaScript** 实现的演出道具交接核验工具。
录入道具与「按分钟标记」的交接记录（道具、交出者、接收者），应用按时间重放记录、
连成每件道具唯一的交接链，自动定位冲突并提示演出结束仍未归仓的道具；
支持**批量交接预演**——按行填写整批交接，先合并重放、逐件给出提交后的持有人或冲突，
全部通过后一次写入；支持演出中途的**现场盘点**——选定分钟、逐行填报实物持有人，
即时给出该时刻的账实差异；并支持**人员交接责任单**——输入人员与起止分钟，
列出该人在时间窗内逐次接收、交出的道具明细，并汇总窗口起点交接前、终点交接后的持有道具；
并支持**出场时段到位核对**——逐行填写道具、出场演员与起止分钟（左闭右开），
一次只读调用核对多行在整个出场区间是否始终由该演员持有；
还支持**交接冲突修复预演**——在核验卡片选定一件冲突道具，围绕首个冲突分钟逐条枚举
单条记录改动（删除 / 改交出者），按同分钟唯一链规则整链重放，只展示整链无冲突的方案，
预演只读、不自动修改记录。
并支持**交接记录变更影响预演**——从交接记录表选择一条记录，输入新的分钟、交出者、
接收者、备注或选择删除，按现有规则校验后只读模拟（不写入记录或签收）；针对该道具
分别重放变更前后的同分钟唯一链、按当前内容指纹核对双方签收，页面并排显示首个冲突、
最终持有人、已核实前缀及其阻断记录，并列出因此失效的签收，结果带数据版本、版本变化时
提示重新预演。
并支持**交接双方签收**——每条交接记录可由交出者、接收者分别输入本人姓名确认
（须与记录中对应角色一致），两侧签收状态独立并持久保存；页面提交确认时携带记录内容指纹，
服务端核对道具、分钟、双方姓名与备注一致后才写入，记录被修改或删除后旧签收立即失效，
过期页面的确认请求会被拒绝；并可按道具与截止分钟查询**已核实交接链**——
沿同分钟唯一链重放，只有双方均有效签收的记录才延伸已核实链，
遇首条缺签或原链冲突即停止，返回阻断记录与此前最后已核实持有人。
还支持**跨道具补签计划**——输入截止分钟与最多 12 次补签额度，对每件道具沿现有
同分钟唯一链重放并核对签收内容指纹，只从当前已核实前缀起连续补齐
（一条记录缺两侧耗两次、缺一侧耗一次，已有有效签收不耗额度；原链首个冲突之后的记录不得规划），
跨道具选择延伸前缀使新增已核实记录总数最大，同收益先取补签次数更少的方案、再按待签列表
（道具 ID、记录分钟、记录 ID、签收方）取字典序最小；结果列出待签姓名与记录、各道具新增长度，
点击记录可打开现有签收弹窗，计划只读、实际签收后自动重新计算。
并支持**道具连续离仓超时排查**——输入截止分钟与允许离仓分钟数，按现有同分钟唯一交接链
逐件重放截止时刻内的记录，把每次从仓库交出至重新入仓视为一个离仓区间（半开区间，时长为止点减起点）；
同分钟多次转手只按该分钟交接完成后最终是否在仓判断，未归仓区间截至查询时刻。
时长严格超过阈值才列为超时（等于阈值不算）；遇交接链冲突时只保留冲突前可确定的区间——
此前已越过阈值仍列为确定超时，冲突后的时长标为无法判定。
并支持**人员同时持有上限排查**——输入人员、起止分钟与持有件数上限，沿现有同分钟唯一交接链
逐件重放窗口内记录，以交接分钟为边界合并各道具在该分钟全部交接后的持有人，
列出已知持有数超过上限的连续分钟段、已知峰值与涉及道具；冲突道具自冲突分钟起视为未知，
已知持有数已超上限时仍判确定超限，否则含未知道具的时段标为无法判定（未知不计为零），
窗口结束分钟之后的冲突不影响结果。
并支持**人员交接忙时排查**——输入人员、起止分钟、窗口长度与交接次数上限，
对起止范围内每个整数起点取半开滑动窗口 [起点, 起点+窗口长度)，逐件沿现有同分钟唯一交接链
重放并统计该人员作为交出者或接收者参与的交接次数（同分钟链式交接按实际可接续记录逐条计数，
与录入顺序无关）；计数以完整确定的分钟为边界——某道具同分钟内先有可接续交接、随后才发生
歧义或断链时，该分钟的部分记录不计入已知，只计早于首个冲突分钟的记录，窗口覆盖冲突分钟时
仍标注冲突，其他已知次数超过上限仍判确定超限，否则标为无法判定（冲突分钟及以后不当作零）；
相邻同结论的窗口起点合并为起点段，返回已知峰值、涉及记录与冲突道具。

## 一条命令启动（Docker Compose）

```bash
docker compose up -d --build
```

启动后访问：

- **应用地址：** <http://localhost:3000>
- 核验结果接口（JSON）：<http://localhost:3000/api/verify>
- 批量交接预演接口（POST JSON）：`http://localhost:3000/api/records/batch/preview`，页面入口为右上角「🧪 批量交接预演」
- 现场盘点接口（POST JSON）：`http://localhost:3000/api/inventory/check`，页面入口为右上角「🔍 现场盘点」
- 人员交接责任单接口（GET 只读）：`http://localhost:3000/api/responsibility?person=张三&start=0&end=12`，页面入口为右上角「📋 人员交接责任单」
- 出场时段到位核对接口（POST JSON，只读）：`http://localhost:3000/api/appearance/check`，页面入口为右上角「🎭 出场时段核对」
- 交接冲突修复预演接口（POST JSON，只读）：`http://localhost:3000/api/conflict-fix/preview`，页面入口为右上角「🛠 冲突修复预演」（冲突道具的核验卡片内也有同名按钮，可直接对该道具预演）
- 交接记录变更影响预演接口（POST JSON，只读）：`http://localhost:3000/api/change-impact/preview`，页面入口为右上角「🧯 变更影响预演」（右下交接记录表每行的「影响预演」按钮可直接选中该记录）
- 交接双方签收接口（GET 查看 / POST 确认）：`http://localhost:3000/api/records/<记录ID>/signoff`，页面入口为右下交接记录表每行的「签收」按钮
- 已核实交接链接口（GET 只读）：`http://localhost:3000/api/verified-chain?propId=p_sword&minute=12`，页面入口为右上角「✅ 已核实交接链」
- 跨道具补签计划接口（GET 只读）：`http://localhost:3000/api/signoff-plan?minute=12&budget=12`，页面入口为右上角「🧩 跨道具补签计划」
- 道具连续离仓超时排查接口（GET 只读）：`http://localhost:3000/api/away-timeout?minute=30&threshold=10`，页面入口为右上角「⏱ 连续离仓超时排查」
- 人员同时持有上限排查接口（GET 只读）：`http://localhost:3000/api/holding-limit?person=张三&start=0&end=12&limit=2`，页面入口为右上角「👥 持有上限排查」
- 人员交接忙时排查接口（GET 只读）：`http://localhost:3000/api/busy-window?person=张三&start=0&end=12&window=3&limit=2`，页面入口为右上角「📈 交接忙时排查」

停止：

```bash
docker compose down
```

> 首次启动时会自动安装依赖；数据文件不存在时会自动初始化一份演示数据（4 件道具，
> 分别覆盖「正常归仓 / 多条可接续冲突 / 断链冲突 / 结束未归仓」四种情形），
> 便于直接看到核验效果。删除 `data/store.json` 后重启可恢复初始演示数据。

## 必要配置

配置通过环境变量 / Compose 完成，均有默认值，通常无需修改：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `HOST_PORT`（compose） | `3000` | 宿主机映射端口。换端口：`HOST_PORT=8080 docker compose up -d --build` |
| `PORT`（容器内） | `3000` | 服务监听端口，修改时需同步修改 `docker-compose.yml` 的端口映射右侧与 healthcheck |
| `DATA_FILE`（容器内） | `/app/data/store.json` | 本地 JSON 数据文件路径 |
| 数据持久化卷 | `./data:/app/data` | 数据保存在宿主机 `./data/store.json`，重建容器不丢数据 |

非 Docker 本地运行（需要 Node.js ≥ 18）：

```bash
npm install
npm start          # 默认 http://localhost:3000
PORT=8080 DATA_FILE=./data/store.json npm start
```

## 使用说明

### 数据录入

- **录入道具**：名称（必填，不可重名）+ 备注。每件道具初始持有人恒为「仓库」。
- **录入交接记录**：选择道具、填写分钟（非负整数）、交出者、接收者（二者不可相同）、备注。
- 道具与记录均可随时**修改、删除**；删除道具会级联删除其名下全部记录。
- 每次增删改后自动重新核验，也可点击右上角「↻ 重新核验」手动重放。

### 核验规则

1. 每件道具初始归「仓库」。
2. 取该道具的全部记录按**分钟升序**逐分钟重放。
3. 在同一分钟内，把记录视为有向边，从当前持有人出发寻找交出者匹配的记录：
   - **恰好 1 条可接续** → 执行交接，持有人变为接收者，并可继续匹配本分钟剩余记录
     （因此同一分钟内 `A→B、B→C` 的链式交接，无论以什么顺序录入都能识别）；
   - **存在 ≥ 2 条可接续记录**（当前持有人同时要交给多个人）→ 判定为
     **「多条可接续记录」冲突，交接链不唯一**，定位这些记录并说明原因；
   - **该分钟有记录但没有一条能从当前持有人交出** → 判定为
     **「剩余记录无法接续（断链）」冲突**，定位当前持有人与冲突分钟的记录。
4. 记录全部重放完毕后，持有人仍不是「仓库」→ 提示**演出结束未归仓**。
5. 引用了已删除道具的记录会被标记为「孤儿记录」，不参与任何道具的核验。

### 批量交接预演（整批录入）

点击右上角「**🧪 批量交接预演**」（应用地址 <http://localhost:3000>）：按行填写
**道具、分钟、交出者、接收者**（校验规则与单条记录完全一致），点击「开始预演」后逐件查看结果，全部通过才能「确认提交」。

预演与提交规则：

1. **预演不落盘**：服务端把整批记录与当前数据合并，沿用同分钟唯一链规则整体重放，
   只返回即时结果，不改写任何交接记录。
2. **逐件结论**：每件受影响道具给出「提交后的持有人」（已归仓 / 演出结束未归仓，未归仓不阻止提交）
   或冲突说明，并**定位涉及的批次行号**（点击行号可滚动高亮对应批次行，冲突行整行标红；
   冲突命中的既有记录编号一并给出）。
3. **禁止提交**：受影响道具**原本已冲突**（即使本批次恰好能接续）或**合并后冲突**时，
   标明原因并禁止提交，需先处理冲突再重新预演。
4. **提交需重新核对**：提交时服务端核对预演所用的**数据版本**与**整批内容指纹**，
   预演后数据被修改（版本过期）或批次内容有任何改动，都会返回 `409` 要求重新预演。
5. **一次写入**：核对通过后整批记录随一份完整快照单次落盘（临时文件 + 原子重命名，
   成功后才发布缓存），不会留下部分记录；落盘失败返回 JSON 500，数据版本不变、
   预演票据仍有效，写入恢复后可直接重试提交。写入后页面自动刷新记录列表与核验结果。

### 现场盘点（演出中途）

点击右上角「**🔍 现场盘点**」：选择盘点时刻（非负整数分钟），逐行填写
**道具名称 + 该时刻实物持有人**（可点「按已登记道具补齐」快速生成待填行），提交后页面展示账实差异表。

盘点规则：

1. 服务端**只重放盘点分钟及以前**的交接，沿用上面的同分钟唯一链规则，
   并在**该分钟所有交接完成后**取账面持有人；晚于盘点时刻的记录与冲突不影响本次盘点。
2. 盘点行逐行定性：
   - **一致**：名称已登记、链可重放，实物持有人与账面持有人相同；
   - **持有人不符**：名称已登记、链可重放，但实物持有人与账面持有人不同（同时给出账面持有人）；
   - **账外**：名称未在道具清单登记；
   - **重复录入**：同一名称在盘点行出现多次——每行**单列**、不以后项覆盖前项，且不参与账实比对；
   - **无法判定**：名称已登记，但其交接链在盘点分钟及以前已冲突（账面持有人不可知）；
   - **未盘**：已登记道具在盘点单中完全没有出现（系统补列一行，持有人留空）；未盘道具若此前已冲突，同样标为「无法判定」。
3. 结果顶部按类别汇总并给出「账实差异」行数（除「一致」「重复录入」外均计为差异）。
4. 盘点**只生成即时结果，不改写任何交接记录**；切换页面数据后旧结果可直接关闭。

### 人员交接责任单

点击右上角「**📋 人员交接责任单**」：输入**人员姓名**与**起始、结束分钟**（均为非负整数，
**起止分钟均包含**在收支明细内），点击「查询责任单」后页面展示该人的责任单。

责任单规则：

1. 沿用核验的**同分钟唯一交接链**规则逐件重放道具记录（只读，不改写任何交接记录）。
2. **收支明细**：按实际接续顺序（分钟升序，同分钟链式交接按链内次序）列出窗口内该人
   每一次**接收 / 交出**的道具与对应记录（分钟、道具、交出者、接收者、备注、记录编号，
   点击记录编号可在右下记录表中定位）。
3. **持有汇总**：
   - **窗口起点交接前持有**：只走起始分钟之前的交接后该人持有的道具；
   - **窗口终点交接后持有**：结束分钟（含）的全部交接完成后该人持有的道具。
4. **无法判定**：交接链在**窗口前或窗口内**发生冲突（冲突分钟 ≤ 结束分钟）的道具单列，
   标明冲突分钟与冲突类型，**不计入确定持有与收支**；
   **窗口结束分钟之后才发生的冲突不影响本次结果**。
5. 人员姓名为精确匹配；「仓库」也可作为查询对象（无交接记录的道具全程在仓库）。

### 出场时段到位核对

点击右上角「**🎭 出场时段核对**」（应用地址 <http://localhost:3000>）：逐行填写
**道具名称、出场演员、起始分钟、结束分钟**（均为非负整数，区间**左闭右开 `[起始, 结束)`**，
即出场覆盖第起始分钟至第结束分钟前一分钟，至少 1 分钟），一次提交核对多行。

核对规则：

1. 服务端沿用核验的**同分钟唯一交接链**规则（只读，不改写任何交接记录），
   只重放**结束分钟之前**（`minute < end`）的交接：**起点分钟的交接计入**
   （起点取该分钟全部交接完成后的持有人），**终点分钟的交接不计入**。
2. 核对点为**出场起点**与**区间内每个交接分钟**（`start ≤ m < end`），均取该分钟全部交接完成后的持有人；
   交接分钟之间持有人不变，这些核对点即可覆盖整个出场区间。
3. **按时间顺序取首个不符或链冲突**，每行只返回第一个问题：
   - **✕ 未到位（持有人不符）**：返回该分钟、实际持有人，以及**导致该状态的交接记录**
     （此前从未交接、道具始终在仓库时该记录为空）；
   - **？ 无法判定（链冲突）**：起点或区间内发生多条可接续 / 断链冲突，返回冲突分钟与定位记录，
     **冲突后的记录不作为确定持有**；起点之前（含起点分钟）的冲突同样使起点无法判定；
   - 先于冲突发生的不符仍按时间顺序优先返回（先不符即报不符）。
4. **全部核对点持有人均为该出场演员 → ✓ 到位**；**区间结束分钟及以后才发生的冲突不影响结果**。
5. 名称未在道具清单登记的行单列为**账外**；结果可点记录编号在右下记录表中定位。

### 交接冲突修复预演（只读，只枚举单条记录改动）

点击右上角「**🛠 冲突修复预演**」，或直接在某件冲突道具的核验卡片中点击
「**🛠 冲突修复预演（只改一条记录，整链重放）**」（自动选中该道具）：
从下拉框选择一件交接链冲突的道具后即时预演，无需提交。

候选枚举与判定规则：

1. 系统沿用核验引擎定位该道具的**首个冲突分钟**及冲突类型（歧义 / 断链），
   围绕该分钟只枚举**单条记录改动**：
   - **歧义（同一分钟多条可接续记录）**：对每条**可接续记录**逐条尝试**删除**——
     删掉其中一条后该分钟若仍能唯一归约，才可能成为方案；
   - **断链（剩余记录无法接续）**：对当分钟**剩余记录**逐条尝试**删除**，
     或把该记录的**交出者改为冲突前持有人**（断裂发生时的当前持有人）；
     新交出者不得与接收者相同（不生成「自己交给自己」的候选），实际无变化的改动也不枚举。
2. **每个候选都按现有同分钟唯一链规则重放该道具的全部记录**：
   改动后在本分钟或之后任何分钟仍出现歧义 / 断链冲突的候选一律排除；
   只有**整链无冲突**的候选才作为方案展示（含被删除 / 被修改的改动记录、
   改动后的完整交接链、**最终持有人**及其**演出结束未归仓**状态——未归仓不影响方案成立，仅如实标注）。
3. **无可行单条修复时明确提示**：所有候选重放后整链仍冲突，会说明尝试过的候选数量与结论，
   提示人工核对更早分钟或冲突之后的记录，不提供任何自动修复入口。
4. **预演只读**：服务端只读取数据并即时重放，**不写入、不自动修改任何交接记录**，
   数据版本 `rev` 不变。方案中列出的每条记录编号都可点击，关闭弹窗后
   **滚动定位并高亮右下记录表中的原记录**，人工核实后再用现有「修改 / 删除」功能编辑。

### 交接记录变更影响预演（只读，模拟一次改动对后续核实的影响）

点击右上角「**🧯 变更影响预演**」，或直接在右下交接记录表某行点击「**影响预演**」
（自动选中该记录）：从下拉框选择一条交接记录后，输入新的**分钟、交出者、接收者、备注**，
或把模拟操作切为「**删除该记录**」，点击「开始预演」。

预演规则：

1. **按现有规则校验**：模拟入参与单条记录录入 / 修改完全一致（非负整数分钟、
   交出者 / 接收者非空且不相同）；实际无变化的修改会被拒绝。引用已删除道具的
   孤儿记录无法按道具重放，不接受预演。
2. **只读模拟、绝不落盘**：服务端只构造「变更后」的临时记录集合，
   **不写入、不删除任何交接记录，也不写入或清除任何签收**，数据版本 `rev` 不变。
3. **变更前后并排重放**：针对该道具分别用变更前、变更后的记录集合，沿现有
   **同分钟唯一链**规则重放**全部记录**，每侧给出状态（已归仓 / 结束未归仓 /
   交接链冲突 / 无记录）、**首个冲突**（类型、分钟、冲突前持有人、定位记录）、
   **最终持有人**与完整重放链（被修改记录在变更后链中高亮，删除则不在变更后链中）。
4. **按当前内容指纹核对双方签收**：两侧都复用已核实交接链逻辑，模拟数据沿用当前
   持久化的签收列表逐条核对内容指纹——**被修改记录的旧签收在模拟结果中立即失效**
   （指纹与模拟内容不符），被删除记录不再参与重放。每侧给出**已核实前缀**、
   最后已核实持有人与**阻断记录**（缺签侧 / 原链冲突）。
5. **列出因此失效 / 受影响的签收**：
   - 被修改记录本身当前仍有效的旧签收（原因：**记录内容已修改，指纹失效**）；
   - 被删除记录本身当前仍有效的旧签收（原因：**记录在模拟中被删除**）；
   - 变更前在已核实前缀中、变更后掉出前缀的**其他记录**（原因：**不再计入变更后的
     已核实前缀**——签收本身仍与记录内容相符，但因链断裂 / 阻断点前移而影响后续
     核实结果）；同时单列改动后**新计入**已核实前缀的记录（例如改动恰好消除了冲突）。
6. **数据版本过期提示**：结果携带生成时的 `rev`；预演面板打开期间若数据被其他操作
   改动（版本变化），面板顶部提示「数据版本已变化，结果可能过期」并提供
   「**重新预演**」按钮，以上一次的改动参数按最新数据重放。
7. 结果中的所有记录编号都可点击，关闭面板后**滚动定位并高亮右下记录表中的原记录**，
   人工核实后再用现有「修改 / 删除」功能真正编辑。

### 交接双方签收

右下交接记录表每行有「**签收**」列与按钮：点击后弹出签收窗口，显示该条记录的
道具、分钟、交出者、接收者、备注及两侧当前签收状态；选择签收方（交出者 / 接收者）并
**输入与所选角色完全一致的姓名**后确认。两侧签收互不影响，可先后分别完成，
状态随数据文件**持久保存**（重启不丢）。

签收规则：

1. **姓名须匹配角色**：服务端逐字核对签收姓名与记录中对应角色（交出者 / 接收者），
   不一致返回 `400` 且不写入。
2. **内容指纹核对**：打开签收窗口时服务端下发该记录的**内容指纹**
   （道具、分钟、双方姓名、备注的 SHA-256），页面提交确认时携带该指纹；
   服务端按当前记录重新计算并核对，**一致才写入**——记录在此期间被他人修改
   （页面数据过期）时返回 `409`，需刷新后重新确认。
3. **编辑 / 删除即失效**：记录被修改或删除后，其全部旧签收**立即失效**
   （服务端在编辑 / 删除时清除，并以指纹校验兜底）；删除道具时级联删除的记录，
   其签收一并清除。
4. 记录表「签收」列实时显示两侧状态：`交 ✓ / 接 ✓` 为已签收，`未签` 为待确认；
   双方均签收的记录才可用于延伸下文的已核实交接链。

### 已核实交接链查询

点击右上角「**✅ 已核实交接链**」：选择**道具**与**截止分钟（含）**，服务端沿
**同分钟唯一链**规则重放该分钟及以前的记录，返回已核实交接链（只读，不改写任何数据）。

判定规则：

1. 沿重放顺序逐条检查：**只有交出者与接收者均有效签收**（签收指纹与当前内容一致）
   的记录才延伸已核实链，最后已核实持有人随之前移。
2. **遇首条缺签记录即停止**：返回该阻断记录（分钟、交出者、接收者、缺签侧）
   与**此前最后已核实持有人**；阻断记录及其后的记录**均不计入已核实**，
   即使其后的记录双方都已签收。
3. **遇原链冲突即停止**：若重放链本身在某一分钟冲突（多条可接续 / 断链），
   已核实链延伸至冲突前的最后一条双方签收记录，返回冲突分钟、类型与定位记录。
4. 窗口内全部记录双方签收齐全 → `VERIFIED`；窗口内无交接记录 → `NO_RECORDS`
   （持有人始终为仓库）。

### 跨道具补签计划（只读规划，实际签收后重新计算）

点击右上角「**🧩 跨道具补签计划**」：输入**截止分钟（含）**与**补签额度**
（0–12 的非负整数，最多 12 次），服务端对每件道具即时规划并返回最优计划
（只读，不写入任何签收或记录）。

规划规则：

1. **逐件重放并校验指纹**：对每件道具沿用**同分钟唯一链**规则重放截止分钟及以前的记录，
   逐条核对签收内容指纹（与当前记录内容不一致的旧签收视为缺签）。
2. **只从当前已核实前缀起连续补齐**：每件道具的「已核实前缀」= 重放链开头连续、
   双方均有效签收的记录；计划只能紧接着该前缀向后**逐段连续**补齐，
   不得跳过任何缺签记录——缺口之后即使已有双方签收的记录，也必须先补齐缺口才会随延伸计入。
3. **额度消耗**：一条计划记录**两侧都缺签消耗 2 次**、**只缺一侧消耗 1 次**；
   **已有有效签收（双方齐全）的记录不消耗额度**（缺口补齐后自动延伸，计入新增但不耗额度）。
4. **原链首个冲突之后的记录不得规划**：重放链在歧义 / 断链分钟停止，
   冲突当分钟与之后分钟的记录（不在唯一链上）一律不可规划，结果中单列冲突道具、
   冲突分钟 / 类型与不可规划记录条数。
5. **跨道具择优（分组背包）**：每件道具可选「不补」或「补齐连续的前 k 条链上缺签记录」，
   在总额度内使**新增已核实记录总数最大**；
   **同收益先取补签次数（额度消耗）更少的方案**；仍相同时，把方案的待签列表按
   **道具 ID、记录分钟、记录 ID、签收方**（`from` 交出者先于 `to` 接收者）排序后，
   取**字典序最小**的方案。
6. **结果内容**：
   - **待签列表**：每项给出道具、分钟、交出者 / 接收者、**待签方与待签姓名**
     （姓名即该记录对应角色，签收时须逐字一致）与记录编号；
   - **各道具新增长度**：已核实前缀长度、本次新增已核实条数、消耗补签次数、
     计划记录与因额度不足未覆盖的连续尾部；
   - 待签列表与各道具计划中的**记录编号均可点击**，直接打开该记录现有的
     **交接双方签收弹窗**完成实际签收。
7. **计划只读、签收后重算**：计划本身不产生任何签收 / 修改；在弹窗中完成实际签收后，
   面板会按原参数**自动重新计算**；若计划生成后数据被其他操作改动，面板顶部提示
   「计划已过期」并提供「重新计算计划」按钮。

### 道具连续离仓超时排查（只读）

点击右上角「**⏱ 连续离仓超时排查**」：输入**截止分钟（含）**与**允许离仓分钟数（阈值）**，
服务端对每件道具沿用**同分钟唯一交接链**逐件重放截止时刻内（截止分钟及以前）的记录并即时返回
（只读，不写入任何交接记录或签收）。

排查规则：

1. **离仓区间**：每次持有人由「仓库」变为非仓库（从仓库交出）起，到重新变回「仓库」
   （重新入仓）止，视为一个离仓区间。区间为半开 `[起始, 止点)`，**时长 = 止点 − 起始分钟**，
   与出场核对、持有时间轴的半开区间口径一致。
2. **同分钟多次转手只看最终状态**：同一分钟内链式交接（如 仓库→张三、张三→李四）
   全部归约完成后，最终在仓则区间结束、最终离仓则区间继续（或新开）；
   同分钟内交出又归仓（最终仍在仓）不产生离仓区间。
3. **未归仓区间截至查询时刻**：截止分钟的交接全部完成后仍离仓的，区间为开放区间，
   止点取截止分钟，时长 = 截止分钟 − 离仓起始分钟。
4. **等于阈值不算超时**：只有时长**严格大于**允许离仓分钟数的区间才列入超时清单；
   每个超时区间给出**起止分钟、时长**与区间内**关联交接记录**（分钟、交出者、接收者、记录编号）。
5. **交接链冲突时的处理**：冲突分钟当分钟的最终持有人无法判定——
   - 冲突前已完整重新入仓的区间照常保留；
   - 冲突前已离仓且仍未归仓的开放区间，可确定时长只算到**冲突分钟开始**
     （`conflictMinute − startMinute`）：若该时长已严格超过阈值，仍列为
     **确定超时**（`CONFIRMED_TIMEOUT`，止点为冲突分钟，并注明冲突后无法判定）；
     否则该区间单列为**时长无法判定**（`UNDETERMINED`，给出冲突前可确定时长），
     冲突当分钟及之后是否仍离仓、何时归仓均不下结论；
   - 窗内发生冲突的道具在结果中另列冲突分组（冲突分钟 / 类型 / 原因）。
6. **截止分钟之后的记录不参与**：更晚的交接与冲突不影响本次排查。

### 人员同时持有上限排查（只读）

点击右上角「**👥 持有上限排查**」：输入**人员姓名、起始分钟、结束分钟（起止均含）**
与**持有件数上限**，服务端沿现有**同分钟唯一交接链**逐件重放窗口内记录并即时返回
（只读，不写入任何交接记录或签收）。

排查规则：

1. **以交接分钟为边界**：状态点取窗口起始分钟 + 窗口内全部交接分钟（含冲突分钟），
   每个状态点取各道具在该分钟**全部交接完成后**的持有人；交接分钟之间持有状态不变，
   相邻同值状态点合并为**连续分钟段**（半开区间 `[起始, 止点)`，末段延伸至结束分钟末尾）。
2. **超限判定**：某时段**已知持有数**（确定由该人持有的件数）**严格超过**上限才列为
   **确定超限**（等于上限不算）；每个超限段给出起止分钟、已知持有件数与**涉及道具**，
   段内仍含未知道具时一并标注（实际持有可能更多）。
3. **冲突道具自冲突分钟起视为未知**：冲突当分钟的最终持有人即无法判定，该道具在
   冲突分钟及以后的时段一律记为未知；**已知持有数已超过上限时仍判为确定超限**，
   否则只要该时段仍含未知道具即标为**无法判定**（**不把未知计为零**）。
4. **已知峰值**：窗口内各状态点已知持有数的最大值，及达到峰值的连续分钟段。
5. **窗口外的后续冲突不影响结果**：只重放窗口结束分钟（含）以前的记录，
   更晚发生的交接与冲突不参与本次排查。
6. 人员姓名为精确匹配；「仓库」也可作为查询对象。

### 人员交接忙时排查（只读）

点击右上角「**📈 交接忙时排查**」：输入**人员姓名、起始分钟、结束分钟（窗口起点范围，
起止均含）、窗口长度与交接次数上限**，服务端对起止范围内的**每个整数起点**取半开滑动窗口
`[起点, 起点+窗口长度)`，逐件沿现有**同分钟唯一交接链**重放并即时返回
（只读，不写入任何交接记录或签收）。

排查规则：

1. **逐起点计数**：窗口起点 s 取起始分钟至结束分钟（均含）的每个整数，
   窗口为半开区间 `[s, s+窗口长度)`；统计该人员在窗口内**作为交出者或接收者**参与的
   交接次数——只计沿同分钟唯一交接链重放确认的链上记录，
   **同分钟链式交接按实际可接续记录逐条计数**（如同一分钟 仓库→张三、张三→李四，
   张三计 2 次），与录入顺序无关。
2. **重放范围**：只取最后一个窗口覆盖分钟（`结束分钟 + 窗口长度 − 1`，含）以前的记录，
   更晚的交接与冲突不参与本次排查。
3. **以完整确定的分钟为计数边界**：链上记录中，冲突道具只计**早于首个冲突分钟**的记录；
   某道具同一分钟内先有可接续交接、随后才发生歧义 / 断链时，该分钟并非完整确定——
   该分钟归约出的**部分链记录也不计入已知**（不能仅凭未完成的链计数），冲突分钟及以后的
   记录既不计入已知、也不当作零。无冲突道具的同分钟链仍按每条交接计数。
4. **窗口覆盖冲突分钟**（`起点+窗口长度 > 冲突分钟`，半开窗口末端恰为冲突分钟时不算覆盖）：
   - 其他道具的已知次数（及冲突道具早于冲突分钟的记录）之和**严格超过**上限仍判
     **确定超限**（等于上限不算；未知不会使已超的次数变少）；
   - 否则标为**无法判定**——冲突分钟及以后的记录无法确认，**不把这些记录当作零**。
5. **相邻同结论的窗口起点合并为起点段**：确定超限段给出段内已知峰值次数、
   段内窗口并集覆盖的**涉及记录**（分钟、道具、交出者、接收者、交出/接收角色、记录编号，
   点击可在右下记录表中定位）与触及的冲突道具；无法判定段给出已知次数上限与冲突道具。
   起点段由「已确认交接进入/离开窗口」与「冲突触达阈值」事件扫描直接形成——
   不按跨度逐起点存储窗口、也不展开起点数组，因此数万分钟的大跨度查询（如起点 0～150000、
   窗口 150001）同样即时返回确定结论；段内记录与冲突仍取并集。
6. **已知峰值**：各起点已知交接次数的最大值，及达到峰值的相邻起点段。
7. **冲突道具清单**：重放范围内发生链冲突的道具（冲突分钟、类型、原因）。
8. 人员姓名为精确匹配；「仓库」也可作为查询对象。

## 数据存储

数据保存在本地单个 JSON 文件（默认 `data/store.json`）：

```json
{
  "version": 1,
  "rev": 7,
  "props":    [{ "id": "p_xxx", "name": "青龙剑", "note": "...", "createdAt": 1700000000000 }],
  "records":  [{ "id": "r_xxx", "propId": "p_xxx", "minute": 3, "from": "张三", "to": "李四", "note": "...", "createdAt": 1700000000000 }],
  "signoffs": [{ "recordId": "r_xxx", "side": "from", "name": "张三", "recordHash": "sha256…", "signedAt": 1700000000000 }]
}
```

其中 `rev` 为数据版本号，每次成功提交自增一次，批量交接预演以此核对预演后数据是否被修改。
`signoffs` 为双方签收列表：`side` 取 `from`（交出者）/ `to`（接收者），
`recordHash` 为签收时记录内容（道具、分钟、双方姓名、备注）的 SHA-256 指纹，
记录内容一旦变化，对应签收即失效。

**快照提交**：所有写请求（道具 / 记录的增删改、批量提交、签收确认）统一走同一提交机制——
先把包含全部字段的完整新快照写入临时文件，再原子重命名替换正式文件，
落盘成功后才切换内存缓存。每个成功请求只落盘一次、`rev` 只自增一次；
删除道具的级联记录与签收清理、编辑 / 删除记录时的签收失效，都与主变更合并在同一次快照提交中，
不会留下部分变更。任一步落盘失败返回 JSON 500：缓存、正式数据文件与 `rev` 均保持请求前状态，
临时文件自动清理，写入恢复后重试同一请求即可（批量提交的预演票据在此期间保持有效）；
重启后读取的仍是最后一次成功提交的完整状态。

可直接备份 / 编辑该文件，重启后生效（结构损坏时会自动备份并重置为初始数据）。

## HTTP API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 全部数据（含数据版本号 `rev`）+ 核验结果 |
| GET | `/api/verify` | 仅核验结果 |
| POST | `/api/records/batch/preview` | 批量交接预演：提交 `{ rows: [{propId, minute, from, to, note?}] }`，合并当前数据重放，逐件返回提交后的持有人或冲突（含涉及的批次行号）与 `previewId`；只读不落盘 |
| POST | `/api/records/batch/commit` | 批量提交：提交 `{ previewId, rows }`，核对预演数据版本与整批内容指纹，不一致返回 `409` 要求重新预演；通过后一次写入全部记录 |
| POST | `/api/inventory/check` | 现场盘点：提交 `{ minute, rows: [{name, holder}] }`，返回该分钟账实差异（只读，不写数据） |
| GET | `/api/responsibility` | 人员交接责任单：`?person=姓名&start=起始分钟&end=结束分钟`（起止均含），返回窗口内逐次接收/交出明细、起点交接前与终点交接后持有、无法判定道具（只读，不写数据） |
| POST | `/api/appearance/check` | 出场时段到位核对：提交 `{ rows: [{name, actor, startMinute, endMinute}] }`（区间左闭右开，起点分钟交接计入、终点分钟交接不计入），逐行返回到位 / 首个不符（分钟、实际持有人、导致记录）/ 链冲突无法判定（只读，不写数据） |
| POST | `/api/conflict-fix/preview` | 交接冲突修复预演：提交 `{ propId }`，围绕该道具首个冲突分钟枚举单条记录改动（歧义逐条删除可接续记录；断链逐条删除剩余记录或把交出者改为冲突前持有人且不与接收者相同），每个候选整链重放，仅返回整链无冲突的方案（改动记录、完整链、最终持有人、未归仓状态）；无可行单条修复时 `hasFix=false` 并说明（只读，不写数据；道具无冲突返回 400、不存在返回 404） |
| POST | `/api/change-impact/preview` | 交接记录变更影响预演：提交 `{ recordId, action: "UPDATE"|"DELETE", minute?, from?, to?, note? }`（UPDATE 按现有单条记录规则校验，无变化返回 400；记录不存在 404），针对该道具并排重放变更前后同分钟唯一链（首个冲突 / 最终持有人 / 完整链），按当前内容指纹核对双方签收并给出两侧已核实前缀与阻断记录；被修改 / 删除记录旧签收列为失效、掉出已核实前缀的其他签收单列；返回结果含数据版本 `rev`、因此失效 / 受影响签收与新计入已核实记录（只读，不写记录或签收） |
| GET/POST | `/api/props` | 道具列表 / 新增道具 |
| PUT/DELETE | `/api/props/:id` | 修改 / 删除道具（删除时级联清理记录及其签收，与主变更同一次快照提交） |
| GET/POST | `/api/records` | 记录列表 / 新增记录 |
| PUT/DELETE | `/api/records/:id` | 修改 / 删除记录（修改保留原录入时间；编辑 / 删除后该记录旧签收立即失效，签收清理与主变更同一次快照提交） |
| GET | `/api/records/:id/signoff` | 查看一条记录的双方签收状态，返回记录内容、内容指纹 `recordHash` 与两侧签收（指纹不符的旧签收不计入） |
| POST | `/api/records/:id/signoff` | 签收确认：提交 `{side: "from"\|"to", name, recordHash}`，姓名须与对应角色完全一致（否则 400），服务端核对内容指纹（道具、分钟、双方姓名、备注）一致才写入（过期指纹 409）；两侧状态独立并持久保存，同侧重复确认替换旧签收 |
| GET | `/api/verified-chain` | 已核实交接链（只读）：`?propId=道具ID&minute=截止分钟`（含），沿同分钟唯一链重放，仅双方均有效签收的记录计入；遇首条缺签或原链冲突即停止，返回阻断记录 / 冲突与此前最后已核实持有人，后续记录不计入已核实 |
| GET | `/api/signoff-plan` | 跨道具补签计划（只读）：`?minute=截止分钟&budget=补签额度`（分钟为非负整数、额度为 0–12 的整数），逐道具沿同分钟唯一链重放并校验签收指纹，只从当前已核实前缀起连续补齐（缺两侧耗 2 次、缺一侧耗 1 次、已有效签收不耗额度；原链首个冲突之后的记录不规划），按「新增已核实总数最大 → 补签次数更少 → 待签列表（道具ID/分钟/记录ID/签收方）字典序最小」择优；返回待签姓名与记录、各道具新增长度 / 消耗 / 未规划尾部、冲突道具清单与计划生成时的数据版本 `rev`（不写数据） |
| GET | `/api/away-timeout` | 道具连续离仓超时排查（只读）：`?minute=截止分钟&threshold=允许离仓分钟数`（均为非负整数），逐道具沿同分钟唯一链重放截止分钟及以前记录，把从仓库交出至重新入仓视为半开离仓区间（时长=止点−起点），同分钟多次转手只按最终是否在仓判断、未归仓区间截至截止分钟；时长严格大于阈值才超时，返回超时区间（起止分钟 / 时长 / 关联交接记录）、冲突前未越阈值的无法判定区间（冲突前可确定时长）与窗内冲突道具清单（不写数据） |
| GET | `/api/holding-limit` | 人员同时持有上限排查（只读）：`?person=姓名&start=起始分钟&end=结束分钟&limit=持有件数上限`（起止均含，均为非负整数），沿同分钟唯一链逐件重放窗口内记录，以交接分钟为边界合并各道具在该分钟全部交接后的持有人；已知持有数严格超过上限的连续分钟段列为确定超限（含涉及道具与段内未知道具标注），冲突道具自冲突分钟起视为未知——已知已超上限仍判确定超限，否则含未知的时段标为无法判定（未知不计为零）；返回超限段、无法判定段、已知峰值及达到峰值的段、涉及道具与窗内冲突道具清单（不写数据） |
| GET | `/api/busy-window` | 人员交接忙时排查（只读）：`?person=姓名&start=起始分钟&end=结束分钟&window=窗口长度&limit=交接次数上限`（起止为窗口起点范围、均含，均为非负整数，窗口长度为不小于 1 的整数），对每个整数起点取半开滑动窗口 [起点, 起点+窗口长度)，沿同分钟唯一链逐件重放并统计该人员作为交出者/接收者参与的已确认交接次数（无冲突的同分钟链按每条交接逐条计数，与录入顺序无关）；计数以完整确定的分钟为边界——冲突道具只计早于首个冲突分钟的记录，同分钟先有可接续交接、随后才歧义/断链时该分钟的部分记录不计入已知；窗口覆盖冲突分钟时仍标注冲突，其他已知次数超上限仍判确定超限、否则标为无法判定（冲突分钟及以后不当作零）；相邻同结论起点合并为起点段，返回确定超限段（段内峰值次数、涉及记录、冲突道具）、无法判定段、已知峰值及达到峰值的起点段、涉及记录与冲突道具清单（不写数据） |
